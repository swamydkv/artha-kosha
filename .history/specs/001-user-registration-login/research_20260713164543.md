# Research: User Registration and Login

## Decision: Authentication MVP architecture

The feature will be implemented as a modular monolith with:

- a Go REST API in `apps/finance-api`
- a Next.js + TypeScript web client in `apps/web`
- PostgreSQL as the system of record
- OpenAPI contracts in `api/openapi`
- `sqlc` query definitions in `apps/finance-api/sql`
- versioned SQL migrations in `apps/finance-api/migrations`

## Rationale

This aligns with the project constitution, keeps the first vertical slice focused, and avoids introducing distributed architecture or service sprawl before there is measurable operational need. The request to use Go, PostgreSQL, OpenAPI, sqlc, and database migrations is directly compatible with the constitutional standards.

## Alternatives considered

- Directly implementing the auth flow in a single frontend-only app with mock persistence.
  - Rejected because it would not satisfy the constitutional requirement for a Go backend, OpenAPI-first design, and PostgreSQL-backed persistence.
- Introducing a microservice and queue-driven auth architecture.
  - Rejected because the constitution forbids unnecessary distributed complexity for a first feature slice.
- Using an ORM instead of `pgx` + `sqlc`.
  - Rejected because the constitution explicitly prohibits ORM usage.

## Resulting constraints

- Registration and login must remain session-based for the MVP.
- Passwords must be hashed using a one-way algorithm such as Argon2id.
- The API contract must be finalized before implementation starts.
- Local validation must be runnable through Docker Desktop.
